# AI Resume Tailor

Milestones 1–6: a local-first resume workspace with PDF/DOCX upload, Gemini extraction, approved profile editing, job analysis, evidence-based generation, and local resume persistence. Generated results receive deterministic and semantic factual checks, a bounded correction attempt, an editable preview with original restoration, and local history. PDF/DOCX exports, profile backups/import, selective deletion, responsive previews, accessibility checks, and a production-build CI workflow complete the MVP implementation.

## Run locally

Use Node.js 22.13+ (Node 24 LTS recommended) and npm.

```sh
npm ci
cp .env.example .env.local
# Set GEMINI_API_KEY in .env.local, then:
npm run dev
```

Open http://localhost:3000. Obtain a Gemini API key from Google AI Studio. `GEMINI_MODEL` defaults to `gemini-3.5-flash-lite` for parsing, job analysis, generation, and validation. Choose a model available to your project that supports structured JSON output. Keys stay server-side and must never use a `NEXT_PUBLIC_` prefix. Restart the server after changing environment variables. Without a key, uploads are still stored locally and can be retried later or replaced with a manual draft; AI parsing returns an understandable configuration error.

`postinstall`, `predev`, and `prebuild` copy the installed PDF.js worker into `public/`. This same-origin generated asset is ignored by Git and rebuilt from the locked dependency version. No CDN is used for document processing.

## Workflow

1. Choose or drop one PDF/DOCX, up to 5 MiB. The original is saved to IndexedDB before extraction.
2. Extract text in a browser worker using PDF.js or Mammoth. The UI stays responsive and terminates processing after 45 seconds. DOCX archive metadata is checked for excessive expansion before decompression. PDFs are limited to 100 pages; extracted text to 60,000 characters. Scanned/image-only and password-protected PDFs need a readable, unlocked alternative; OCR is out of scope.
3. Send **only extracted text** to `/api/parse-resume`. Gemini uses a structured JSON schema and extraction-only instructions. Zod validates the result. Lifecycle metadata and fact IDs are assigned by the application, never trusted from AI.
4. Save the draft locally and open `/profile`. Review, correct, and expand every profile section. No upload or autosave can create or overwrite a verified profile. Select **Save & Continue** to validate and approve your information, then open the dashboard.
5. If extraction, networking, AI, or storage fails, retain existing data and show recovery options. A saved original can be retried after reload. Manual draft creation works without AI. Replacement requires confirmation when a draft or verified profile exists. Concurrent draft changes are detected at commit time to avoid overwriting edits in another tab.

AI output is unverified and can contain mistakes despite schema validation. Profile approval records your review; it does not independently prove the truth of entered or extracted facts.

## Profile editing and approval

`/profile` supports personal information and additional websites; multiline headline, summary, and career objective; employment; education; skills with searchable categories across professions and one optional Experience field; projects; certifications; awards; publications; volunteer work; professional memberships; languages; and other accomplishments. Employment and project facts are edited individually. Cards support addition and distinct outlined deletion buttons with confirmation; reorder controls are omitted. Employment type offers standard dropdown choices while retaining saved custom values. Technologies use compact single-line inputs in a responsive grid, with independent add/edit/remove controls. Facts get IDs only when added. React Hook Form uses a separate internal field key so edits and deletions never replace domain evidence IDs. Existing skill proficiency and supporting context display together without modifying stored data; editing the combined Experience input consolidates its text into supporting context. Existing categories and backups remain valid.

Desktop has a section sidebar with completion indicators. The page header places Continue to Dashboard beside the title for approved profiles and keeps Replace resume in an accessible three-dot menu. Save & Continue is the sole normal save action at the bottom of the editor, beside a compact Saved/Saving/Unsaved indicator; actionable storage errors and conflict recovery remain available there. Draft/approved state is shown as a small header badge, without repeated sidebar explanations. Mobile has a compact section menu and collapsible sections. Each field has a label; approval errors open the relevant sections, display inline messages, and focus the first invalid field. Empty optional sections are allowed. A full name is required for approval; added entries must meet the strict section schemas. Unknown dates and experience levels remain blank, and entering current employment clears its end date.

Drafts and approved profiles have deliberately different validation:

- `profileDraftSchema` preserves unfinished entries, partially typed email/URLs, and incorrect date ranges for correction. It still enforces structure, valid IDs, unique IDs, text limits, draft status, and lifecycle integrity. Drafts may contain invalid input and must never be used directly for generation.
- `professionalProfileSchema` remains strict for AI output and approved data. **Save & Continue** uses it to reject invalid fields before approval. `readProfile(db, "verified")` always uses strict validation.

Draft changes autosave after 600 ms through a serialized write queue. There is no redundant Save Draft button. **Retry saving** appears only after a storage failure; Save & Continue explicitly approves the profile. Application links flush pending edits before navigation; the browser warns before unloading with unsaved work. Wait for the saved status before closing the browser or device. Failed storage writes leave the form intact with a retryable error.

Opening an approved profile does not write a draft or change its approval. Editing it creates a separate draft while preserving its IDs and original creation timestamp. The approved copy stays untouched until the next explicit approval. Approval runs in one IndexedDB transaction: validate the complete profile, assign the verification timestamp, increment the approved version, write the approved copy, and remove the reviewed draft. Autosaves are paused/drained before approval so an older pending write cannot recreate that draft. Uploaded-source linkage is preserved. No database-index migration is needed; the existing stores and optional record metadata are reused.

Writes compare both draft and approved snapshots inside the transaction. If another tab saves or approves first, the stale editor stops writing and shows a conflict message; it never silently overwrites the newer profile. Reloading after confirmation discards unsaved local edits and loads the stored version. The dashboard requires an approved profile and shows its version. Each generation rereads the latest approved copy; an unreviewed editor draft is never used.

## Profile as the starting page

`/` redirects to `/profile`. Navigation contains Profile, Dashboard, and Settings, and the logo links to Profile. With no saved draft or approved profile, Profile shows resume upload and manual creation. A saved file without a profile stays available for parsing retry after reload. Successful parsing/manual creation switches to the editor on the same page. Existing drafts and approved profiles open directly in the editor.

**Replace resume** saves pending editor changes before opening the upload experience. Parsing a replacement requires confirmation, preserves the approved profile and original files, and creates an unverified draft for review. **Back to profile** returns without replacing information. Approved profiles retain a direct **Continue to Dashboard** action.

## Milestone 4: job analysis and resume generation

On `/dashboard`, paste a job description (20–30,000 characters), optionally supply company/title, posting URL, and notes, then choose a visual layout (Modern, Classic, or Compact) and target length. Layout cards support mouse, touch, and native radio-button keyboard navigation. Optional details are not required when already present in the description. Progress reports real request stages without percentages. Duplicate submissions are blocked, and failed operations leave the form and saved profile intact.

`/api/generate-resume` accepts the raw description, optional company/title, strictly validated approved profile, and settings. One structured Gemini response contains both job analysis and evidence-based resume selections. Missing company information is left absent. `/api/analyze-job` remains available for standalone analysis but is not called by the tailoring workflow. All AI endpoints use the same streamed 256 KiB body cap, origin check, shared client/global limits, safe JSON responses, no-store headers, and bounded provider calls. Very large profiles may exceed the payload cap; this returns an explicit error without changing local data. Resume/profile content is not persisted or logged server-side by default; the explicit AI debugging switch records request/response content in hosting logs.

Generation is deliberately constrained:

1. Rank verified entries and facts by token overlap with raw job-description text, retaining original order on ties. Gemini analyzes the actual requirements in the same response that writes the resume. Bound selection by target length/emphasis. Send only selected employment/project evidence and skill/education/certification candidates to Gemini; contact details, job URL, and profile lifecycle metadata are excluded. Existing headline/summary are supplied as professional context for refinement.
2. Ask Gemini to select source IDs and rewrite supported bullets. Notes/instructions may guide presentation but cannot supply new qualifications. Prompts treat all supplied content as untrusted and prohibit changing facts, inventing numbers/skills, unsupported leadership, API-development claims from API consumption, or presenting projects as employment.
3. Reject unknown/duplicate entry selections, unknown skill/education/certification IDs, missing or cross-entry bullet evidence, and empty results. Numeric claims are checked in the subsequent validation stage so supported evidence can be used for one bounded correction. Copy employers, titles, dates, project identities, credentials, skills, contact information directly from the approved profile. Headline and summary are rewritten using supported facts and checked during factual validation.
4. Create lifecycle/bullet IDs server-side and preserve the profile ID/version. The candidate begins as `pending-semantic-review`; the client saves this draft before submitting it to `/api/validate-resume`. Unresolved factual errors remain visible on the saved draft and block document export. Warnings remain visible for user review. These checks do not guarantee accuracy.
5. Save the initial draft, original content, approved source profile snapshot, and optional review allowance to IndexedDB, then update the saved draft with its factual review. Offer a link to `/resume/[id]` even when review fails. **Retry factual review** on the dashboard, or **Check facts & save** on the reopened preview, reviews the same draft without analysis or regeneration. The editable single-column preview survives reloads and can be reopened from dashboard history. If local saving fails, the result remains in the current tab and **Retry saving resume** retries local persistence without regeneration, then runs the outstanding review if it has not completed. Closing/reloading before retry loses that unsaved result.

Target length guides selection and concise wording; PDF export reports the actual page count and never truncates content or silently reduces font sizes to force that target. Original uploaded files, approved profiles, and existing resumes are untouched by generation. Schema validation is not proof of factual accuracy, and client-supplied “verified” status records user approval rather than independent verification.

## Milestone 5: validation, editing, and history

`POST /api/validate-resume` accepts a resume, its strictly validated approved source profile, and an optional `correct` flag. It shares all other AI endpoints' size/origin/rate safeguards and no-store responses. Incoming validation metadata is ignored and recomputed. Deterministic checks compare profile ID/version, contact fields, employers, titles, locations, dates/current status, project identities, degrees, skill identifiers/values, and certifications. Bullets require evidence from their own source entry; duplicate identifiers and unsupported numeric tokens are errors. These checks are conservative and do not infer years of experience from dates.

Semantic review sends Gemini each rewritten claim with its actual scoped evidence, excluding contact fields, job requirements, and unrelated instructions. Existing approved headline/summary/project description are trusted verbatim; edited versions are reviewed. Each claim must receive exactly one supported/unsupported/uncertain verdict; missing, duplicate, foreign, malformed, or truncated results fail safely. Prompts explicitly flag invented technologies/metrics, exaggerated responsibilities/seniority, misleading causality, API consumption presented as development, and misattribution. A source ID alone never establishes support.

New generation uses `correct: true`: at most one text-only correction may replace failed claims. It cannot change identities, source IDs, or evidence references. All claims are then rechecked. Unresolved errors leave a saved failed draft for correction/review; it cannot be exported as PDF/DOCX. Structural identity/provenance errors are rejected directly rather than repaired by AI. Provider failures never produce successful validation. Uncertain claims produce visible warnings (`needs-review`), while completed checks with no issues produce `passed`. The endpoint can take up to three 45-second provider calls; the route has a 180-second budget and the client a 155-second timeout. Production hosting must support this duration. No content is persisted server-side.

The preview offers **Edit resume**, **Save changes**, **Check facts & save**, **Restore original**, and reload controls. Text editing preserves all fact/source/bullet IDs; it cannot alter verification metadata. Manual changes immediately clear prior validation and affect only this resume. Saving is explicit; schema failures retain edits. **Check facts & save** reviews and saves the current text without automatically rewriting it. Manual content with errors may be saved as a clearly failed draft for further correction, never marked passed. Unsaved navigation/reloads prompt before discarding changes. A supporting-evidence panel lets users compare each bullet with its original facts.

New records retain an approved source profile snapshot locally, keeping validation tied to the version used for generation even after the current profile changes. Milestone 4 records remain readable; review can use the current approved profile only when ID/version match. Save and restore transactions compare the expected modification timestamp, use monotonically increasing timestamps, preserve the immutable original/source snapshot, and reject stale-tab writes or deleted-record resurrection. Restoring requires confirmation and restores the original generation's review status. Failed writes keep the editor's content available for retry.

Dashboard history uses IndexedDB change subscriptions, sorts by most recently modified, and displays role, company, creation/modification dates, template, and review status. It supports opening, confirmed deletion with stale-record protection, and downloading resume JSON without exporting the full source profile snapshot. Unreadable records are preserved and reported rather than silently removed. Formatted PDF/DOCX downloads are available from the preview and each history entry after factual review.

## Milestone 6: exports and local data management

**Export PDF** and **Export DOCX** appear on the resume preview and in each history entry’s **Document downloads** panel. Unsaved text, pending factual review, and failed validation block formatted exports. Warnings remain visible for review. Export errors leave the saved resume intact and allow retry. JSON history downloads remain available for data recovery, including unfinished resumes.

The dashboard and resume preview offer three layouts with gray-line paper thumbnails: **Modern** (left-aligned sans-serif with section rules), **Classic** (centered header and serif typography), and **Compact** (smaller header, tighter spacing, and narrower margins). Shared layout definitions control typography, alignment, margins, spacing, and rules in the browser, PDF, and DOCX. Layout selection is stored with the resume. Switching in the preview saves only appearance through a stale-tab-safe transaction, preserves unsaved text and factual review, and makes no AI requests. Existing `modern-professional` records remain valid. Layout IDs are excluded from Gemini writing prompts.

Preview and both formats use one plain-text block model (`src/lib/export/document.ts`) to keep contact information, headline/summary, experience, skills, projects, education, honors/coursework, and certifications consistent. AI instructions, notes, validation messages, evidence IDs, and source snapshots are excluded from application documents. Filenames follow `First_Last_Company_Position.pdf`/`.docx`, omit absent job details, preserve Unicode names, and remove unsafe path/control characters.

PDF export uses pdf-lib, embedded openly licensed Noto Sans or Noto Serif Regular/Bold selected by layout, US Letter pages, layout-specific margins (Modern 48, Classic 54, Compact 42 points), readable body text, stable heading spacing, long-word/URL wrapping, widow control, and page numbers. It draws actual text, never screenshots. Text can be selected, searched, and extracted. Headings stay with following content where space permits; long content paginates without clipping. A page-target mismatch is reported after export rather than deleting text. DOCX uses the `docx` library to create editable Word paragraphs, native list numbering, Title/Heading styles, Arial or Times New Roman typography according to layout, matching page size/margins, and keep-with-next/widow controls. Office font substitution and different layout engines can change wrapping and pagination; the browser preview is a flowing preview, not an exact page-break simulation.

Formatting runs in a disposable browser worker with a 45-second limit; document content never leaves the browser for export. Fonts are served from this application’s `/fonts/`, without Google Fonts/CDN requests. PDF export reports missing font glyphs instead of emitting replacement squares; DOCX can use system fonts for other scripts. Export input is capped at 200,000 characters and PDF output at 50 pages to bound work on malformed local data. Failed font downloads, worker startup, encoding, timeouts, or packing do not change stored data.

Settings offers one **Download profile backup** action. Version 2 JSON backups atomically include both the approved profile and any unfinished draft; either version can be absent. Exports and imports are capped at 2 MB. Imports validate both included versions with Zod, prefer unfinished edits for review (otherwise the approved version), and always create an unverified draft. The other version remains preserved in the backup file. Version 1 backups and raw supported profiles remain importable. An existing draft/approval triggers confirmation. Current approved data stays intact until explicit approval, and stale-tab imports are rejected transactionally. Professional fact IDs are preserved; a new profile lifecycle ID/timestamps prevent imported verification/version metadata from impersonating older resume evidence. Imported drafts may contain incomplete fields but cannot be approved until the strict profile schema passes.

Deleting uploaded files removes original Blobs, the retry pointer, and obsolete source-document links while preserving professional facts and resumes. Deleting generated resumes removes their originals and local evidence snapshots while preserving profiles/uploads. **Delete all local data** atomically clears all five IndexedDB stores, including preferences, then reloads the upload screen. Each deletion requires confirmation, and failed multi-store changes roll back. Existing browser downloads are outside the application’s storage and are not deleted.

The UI wraps long resume strings on narrow screens, retains visible keyboard focus and labeled fields, and respects reduced-motion preferences. New Playwright tests exercise the complete upload → approval → tailoring → manual edit → factual review → actual PDF/DOCX download → reload flow, plus backups/import/deletion and automated axe WCAG A/AA checks on desktop and mobile. Export tests verify filenames, character handling, text contents, page bounds, and pending/failed review guards. One-page and four-page fixtures were rendered and visually checked in PDF and DOCX; PDF text extraction was independently verified.

See [deployment and release verification](docs/deployment.md). CI runs type checks, lint, unit/integration tests, a webpack production build, and the complete browser suite against that production build without paid API calls. Local export QA fixtures can be retained with `EXPORT_QA_DIR=/private/tmp/resume-export-qa npm test`; fixture files contain invented test identities only and are not application data.

## Public deployment and API protection

The Next.js app can be built and hosted on Vercel. Before enabling live AI processing, configure:

- `GEMINI_API_KEY`, optionally `GEMINI_MODEL`.
- `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` for shared rate-limit counters.
- `RATE_LIMIT_SALT`, a long random secret used to HMAC client IPs before storage.

Production AI processing **fails closed** if shared Redis, a valid Vercel-provided client IP, or required settings are unavailable. Vercel preview deployments also require shared limiting. New tailoring runs allow 5 starts per client per 10 minutes, independently of standalone parsing/analysis and unreserved review limits. Redis counters contain pseudonymous identifiers and expiration windows, not resume content; analytics are disabled. Client IPs come only from Vercel’s `x-vercel-forwarded-for` header on Vercel deployments. Other production hosting requires adapting the trusted-proxy identity source.

The normal tailoring path uses **two Gemini calls**: combined analysis/writing, then independent factual review. At most one schema repair can add a writing call; a factual correction plus revalidation can add two. Upload parsing is a separate one-time operation. No automatic unbounded retries occur.

Admission reserves up to 11 provider-call units: two writing calls and three factual-review attempts of up to three calls each. A signed allowance binds those reviews to the client, resume, and approved profile ID/version for 24 hours. Redis atomically consumes one allowance per review request. Initial review and two retries bypass new-run admission/global checks because their capacity was reserved already; Redis outages still fail closed. The allowance survives browser reloads in local record metadata and is excluded from resume JSON/PDF/DOCX exports. Expired, exhausted, different-network, or invalid allowances fall back to separately limited reviews without regeneration. Salt rotation also falls back to normal admission.

The shared daily budget is **600 reserved provider-call units**, not a monetary cap: each new run reserves 11, standalone parsing/analysis reserves 1, and unreserved review reserves 3. Unused capacity is not refunded (roughly 54 full run reservations/day before other usage); reservations carry their review allowance across midnight. Reservation counts are conservative and do not charge Gemini for unused calls. Configure provider quotas to enforce actual spending limits. The new Redis prefix is `resume:v2:*`; deploying this version starts new counters. Local `next dev` uses separate in-memory admission buckets of 5 starts/minute, with the same review allowance behavior. This is only a development convenience, **not distributed production protection**. Local `next start` fails closed for AI processing without a trusted production deployment. Tests mock AI/provider calls and do not require a paid key.

The API caps streamed JSON bodies at 256 KiB (including when Content-Length is missing or false), checks origin when supplied, validates input and output, applies provider and client timeouts, returns consistent JSON errors, and sets `Cache-Control: no-store`. Ordinary HTTP errors exclude provider details and personal content; explicitly enabled debugging adds only the calling request’s redacted AI traces. Logs omit that content unless the explicit full-payload debugging switch is enabled. Same-origin checks are supplemental; shared rate limits and the global cap are the cost controls. Additional edge/WAF controls and provider quotas may be appropriate for a public launch.

## Architecture and storage

- Next.js App Router, strict TypeScript, Tailwind CSS 4, and configured shadcn/ui components. Responsive navigation covers `/`, `/profile`, `/dashboard`, `/resume/[id]`, and `/settings`.
- Zod schemas in `src/schemas` are the runtime and inferred-type source of truth. Repeatable professional facts have stable IDs. Dates use `YYYY-MM` only when known; the extraction prompt preserves partial source dates with context in additional accomplishments rather than inventing months.
- Browser extraction, server AI processing, upload orchestration, and persistence are separate modules under `src/lib`. A server-only import guards Gemini credentials and rate-limit code.
- Dexie schema version 1 has `profiles`, `profileDrafts`, `uploadedDocuments`, `generatedResumes`, and `settings`. Singleton profile keys support one professional profile. Draft source document linkage is optional record metadata and requires no index migration. Future indexed changes must append a Dexie version; do not rewrite released version 1.
- Original files are Blobs; no extracted text is stored separately. A latest-upload pointer supports retry. Draft commits occur in transactions, independently of file storage, so a failed operation cannot remove the original or approved data. Invalid stored profiles are rejected without deleting them.
- IndexedDB opens in client effects, never during SSR. Storage/quota failures are surfaced. Generated resume records contain validated structured content plus an immutable original for future restoration. IDs, profile version, timestamps, pending-review status, and evidence IDs are retained. Inserts cannot overwrite existing resumes. An optional approved-source snapshot is added to each new record; old records remain readable. The existing `id, updatedAt` indices suffice, so no IndexedDB version migration is needed.

## Remaining limitations

- Validation is evidence-based review, not a guarantee of truth; users must review the result. Older resumes without a source snapshot cannot be revalidated if their approved profile ID/version no longer matches. Profile JSON is a backup of professional facts, not a full workspace archive: original documents and generated resumes are excluded. Saved resume JSON downloads remain available separately. Local browser storage can be cleared or unavailable.
- PDF fonts cover Latin, Greek, and Cyrillic; unsupported characters are reported with a DOCX fallback rather than silently replaced. RTL/CJK PDF font/shaping support is not included. DOCX appearance and pagination depend on the fonts and Word editor installed on the recipient’s device. Target length guides selection and does not guarantee a fixed number of pages.
- Automated accessibility checks cover WCAG A/AA rules in the core resume/settings flows; they do not replace a complete assistive-technology audit. Browser automation currently uses Chromium desktop and mobile emulation. A GitHub Actions workflow is configured, but no remote CI run or Vercel deployment is claimed.
- Real Gemini output quality still needs a user-run smoke test with configured credentials. Automated provider responses are mocked; no live call is claimed.
- npm audit reports 5 high-severity development lint-chain findings through `eslint-config-next → fast-glob → micromatch → braces` (GHSA-vfj7-8cjw-p6xm). No patched braces successor was available during implementation.
- npm audit also reports 3 moderate findings through Mammoth’s CLI-only `argparse → sprintf-js` chain (GHSA-hp3w-g68c-fv3c). The application imports the browser bundle, which does not include argparse/sprintf; it never invokes Mammoth’s CLI. The suggested forced downgrades are incompatible/obsolete and were not applied. Recheck upstream patches before public release.

## Tailoring quality

The writer prioritizes the role’s central requirements, matches direct and transferable verified experience, and improves specificity, relevance, and emphasis rather than merely shortening the profile. It writes a fresh role-specific headline/summary and preserves substantive accomplishments, technical depth, supported scope/results, and career progression. Automatic chooses length from relevant evidence with no aggregate bullet target, derived minimum, or page target; technical schema ceilings still apply. One-/two-page settings retain evidence-limited content budgets. No “what changed and why” explanation is requested or added to the response format. One-/two-page depth checks, repeated bullets, copied summaries, and major omissions produce advisory `qualityWarnings` on the draft. They never trigger an editorial rewrite or reject an otherwise structurally valid draft. Exact reasons appear in Chrome Console under `[Gemini] Resume quality warnings` (independently of full-payload debugging) and in server warning events. Drafts save before normal deterministic/semantic factual review; warnings survive local reloads, factual review, and manual edits. The dashboard and preview show them as suggestions about the original generated draft. Quality warnings do not block export; pending or failed factual validation still does. One bounded rewrite remains available only for invalid structured output. Preview includes source coverage and a summary comparison; dashboard counts help identify incomplete approved profiles. These checks do not promise an exact page count, stronger hiring outcomes, or an ATS score. See docs/deployment.md for limits and request budgets.

## Debugging AI calls

AI lifecycle metadata and exact schema failure paths are logged server-side for every call. To inspect full prompts and raw responses, explicitly set `AI_DEBUG_LOG_PAYLOADS=true` locally or in Vercel and restart/redeploy. This records resume/job content in server logs and returns request-scoped, credential-redacted traces to the caller. Chrome DevTools Console shows collapsed `[Gemini]` groups for each request, response, repair, and error, with raw payloads and parsed input/output objects. No debugging banner is shown. Known server credentials are redacted. Disable it with `false` after troubleshooting. See docs/deployment.md for the JSON event/chunk format.
